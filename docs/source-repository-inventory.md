## Detailed audit notes: core engine sources

### Shizuku

- Current source uses Apache-2.0. The checkout is Java/Kotlin with C++/JNI components. Its Gradle configuration sets `compileSdk`/`targetSdk` 37, `minSdk` 24, and Java 21.
- Verified candidate paths include `server/src/main/java/rikka/shizuku/server/ShizukuService.java`, `ShizukuUserServiceManager.java`, `api/aidl/src/main/aidl/moe/shizuku/server/IShizukuService.aidl`, `api/api/.../ShizukuBinderWrapper.java`, `manager/src/main/java/moe/shizuku/manager/adb/AdbPairingClient.kt`, `manager/src/main/jni/adb_pairing.cpp`, and `api/rish/src/main/cpp/pts.cpp`.
- OmniShizuku has corresponding `server`, `api`, `starter`, and `shell` modules and similarly named server/AIDL implementations. SHA-256 checks on four server source files show they are not byte-identical to this checkout; treat the target as a modified implementation whose precise provenance and behavioral deltas still need a line-level comparison.
- SDK/JVM compatibility looks plausible from the checked-in configuration, but this source was not integrated or built in this audit. The target baseline build fails on an AAR metadata requirement.

### Shizuku-Next

- Current source uses Apache-2.0. The inspected Android configuration is `compileSdk`/`targetSdk` 36, `minSdk` 24, Java 21 and Kotlin JVM target 21. Its manager has focused unit tests for modules, command review, settings, WebUI policy, output and catalogs.
- Relevant modules include `manager/src/main/java/moe/shizuku/manager/module/ModulePackage.kt`, `AdbModuleManager.kt`, `ModuleWebUi.kt`, and `ModuleJsBridge.kt`; matching module-management code already exists in OmniShizuku.
- The target installer enforces 256 KiB script, 32 MiB unpacked archive and 512-entry limits in `ModulePackage.kt` / `AdbModuleManager.kt`; ZIP names are normalized and checked against staging-root canonical paths. Its WebUI uses a local-file origin check, opt-in shell bridge, explicit command approval, and configurable network access. These are static observations, not a security certification or runtime test.
- Do not copy the Next module engine wholesale: an equivalent target subsystem already exists with different limits and adapters. Compare behavior and tests before selecting small fixes. Focused target tests for new input validators are now present but could not be run because Gradle cannot enumerate network interfaces in this sandbox.

### Canta, ADNS and package-operation validation sources

- Canta is licensed LGPL-3.0 (`LICENSE`), built as Kotlin Multiplatform, and declares Android compile/target SDK 37 with min SDK 28 and Kotlin 2.4.20. Its `BloatRepository.kt` fetches and caches the Universal Android Debloater list; `AdbHelper.kt` rejects invalid package names before shell operations; `packages/PackageOperations.kt` provides status-reported uninstall/reinstall operations.
- The target already has `DebloaterManager`, `UadRepository`, `PackageTools`, and app-management screens. Canta's whole package stack would duplicate these and has a higher min SDK plus a different multiplatform architecture, so it was not added.
- ShizukuPlus `server/.../InputValidationUtils.kt` has a standalone package-name validator (Apache-2.0). A small Kotlin adaptation is now shared by target package-operation call sites; attribution is recorded in the helper. Canta's validator was also used as a comparison, no Canta code was copied.
- ADNS is MIT-licensed (`LICENSE`), Kotlin, compile SDK 36.1 / target 36 / min SDK 27, AGP 9.2.1 and Kotlin 2.2.10. Its `app/src/main/java/com/eyalm/adns/data/provider/PrivateDnsHostname.kt` normalizes IDNs, enforces DNS label/total lengths, requires a multi-label hostname, and rejects numeric IP-like input. Its `DnsProviderCatalog.kt` supplies public provider profiles for AdGuard, Cloudflare, Google, Quad9, OpenDNS, DNSforge and HaGeZi. The target now adapts the hostname parser and the provider profile data without importing ADNS's Android UI or NextDNS account/network stack; `NOTICE` and `licenses/ADNS-MIT.txt` retain the required attribution and MIT terms.
